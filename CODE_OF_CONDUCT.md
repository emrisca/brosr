# Code of conduct

Brosr is a small project about watching things together. The room is the point, so the project
keeps the same rule in issues, pull requests, reviews and discussions: treat the other person as
someone who is here on purpose.

## What that looks like

- Assume the other person read the code and meant well. Ask what they saw before you say they
  are wrong.
- Criticise the change, not the person. "This seeks on every frame" helps. "This is careless"
  does not.
- Say when you are unsure. A question costs a minute, and a wrong guess in the relay costs a
  day.
- Keep a review to the change in front of you. A pull request is not the place to relitigate the
  design, and the design lives in `docs/`.
- Respect a boundary the first time it is named. If someone says a topic is off the table, drop
  it.

## What is not welcome

- Harassment, insults, threats and sustained disruption.
- Comments about a person's body, identity, background, experience level or grammar.
- Sexual attention or imagery where nobody asked for it.
- Publishing someone's private information, including an invite link, a room key or a log that
  carries either.
- Dismissing a report by arguing about intent. Intent matters later, and the behaviour comes
  first.

## Scope

This applies in the repository, in issues and pull requests, in the project's chat and anywhere
someone speaks for Brosr. It also applies to a person who keeps the same behaviour in a project
space after being asked to stop.

## Reporting

Report a problem to the maintainers through GitHub. Open a
[private security advisory](https://github.com/emrisca/brosr/security/advisories/new) when the
report contains anything private, or send a direct message to a maintainer on GitHub when it
does not. The repository has no conduct mailbox, and this file does not invent one.

Say what happened, where and when, and who else saw it. A link to the comment or the pull
request is the most useful thing you can include. The maintainers read every report, keep it
between the people who need it and answer the reporter. They will not ask you to face the person
you reported.

## What happens next

A maintainer reads the report, asks the reporter for anything missing and decides. The response
matches the behaviour rather than the wording of the complaint:

1. A private word, when the behaviour looks like a one-off and the person can correct it.
2. A public note on the thread, when the problem happened in public and the record matters.
3. A pause from the project spaces, when a private word did not hold.
4. A permanent block, for violence, a threat, or a pattern that survives a pause.

The reporter hears the outcome. The person reported hears the reason. Neither hears more detail
about the other than the decision needs.

This document is short on purpose. If a case is not named here, the maintainers use the same
rule the project uses everywhere: does this leave the room better for the next person.
